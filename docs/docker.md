# Docker

The Docker stack is part of **CatWAF Full**. CatWAF Lite does not install it, and
`catwaf docker` refuses to run there.

## Managing the stack with `catwaf docker`

```bash
catwaf docker up            # build if needed and start in the background
catwaf docker up --build    # force an image rebuild first
catwaf docker status        # each service and its state
catwaf docker logs -f       # stream logs from every service
catwaf docker restart
catwaf docker down          # stop and remove containers
catwaf docker build         # rebuild images without starting
```

These wrap `docker compose` against this repository's `docker-compose.yml`. The
subcommand is checked against a fixed allowlist and the argument vector is built
from constants, so nothing you type reaches a command line and no shell is
involved. Either the `docker compose` plugin or a standalone `docker-compose`
binary works; if neither is installed the command says which is missing and
exits `3`.

Running `docker compose` directly does exactly the same thing — `catwaf docker`
is a convenience, not a requirement.

> `catwaf docker` needs access to the Docker daemon. Anyone who can run it can
> already control containers on that host; it grants nothing new.

## Creating the admin account

The stack ships with no accounts — the same rule as every other install path.
The WAF protects the test app from the moment the stack is up, but there is
nothing to log into until you create a login:

```bash
docker compose exec backend node bin/catwaf.js user add admin --role admin
```

It prompts for a password interactively, or reads `CATWAF_USER_PASSWORD` from
the environment for an unattended run:

```bash
docker compose exec -e CATWAF_USER_PASSWORD='…' backend \
  node bin/catwaf.js user add admin --role admin
```

Then open <http://localhost:8081> and sign in. For remote administration use an
authenticated tunnel or configure HTTPS; the shipped HTTP dashboard is loopback-only.

## Architecture

Three containers, matching how CatWAF already works outside Docker (see
[reverse-proxy.md](reverse-proxy.md) and [architecture.md](architecture.md)):

```
   public traffic          ┌──────────────────────┐        origin
   :80 / :443  ───────────▶│  caddy               │──────▶ test-app:8080
   (WAF-inspected)         │  reverse proxy + WAF │        = host :8082
                           │  + dashboard SPA     │        (your real app
   admin dashboard         │                      │         goes here)
   :8081       ───────────▶│                      │──────▶ backend:8000
   (not inspected)         └──────────────────────┘        (API, SQLite state)
```

| Port | What it is |
|---|---|
| `:80` / `:443` | Public traffic for the protected website. Every request here passes through Coraza before reaching the origin. This is how visitors should arrive. |
| `:8081` | CatWAF's admin dashboard — the control panel SPA plus its `/api` and `/g` routes. Kept off `:80` so it can never collide with the site being protected. |
| `:8082` | The protected website's own origin, bound to `127.0.0.1` only. Reaching it directly **bypasses the WAF** — it exists for local inspection and for demonstrating the difference, not as a way in. |
| `:8000` | The backend API, published on loopback for healthchecks. The dashboard reaches it through Caddy. |
| Unix socket | Caddy's admin API at `/run/catwaf-admin/admin.sock`; no TCP listener. |

- **`backend`** — the Node API (`Dockerfile` at the repo root). Owns the
  SQLite database (`catwaf-data` volume) and writes WAF config changes into
  the shared Caddyfile. Runs as the image's unprivileged `node` user, not
  root.
- **`caddy`** (`docker/Caddy.Dockerfile`) — a Caddy binary built with the
  [Coraza module](https://github.com/corazawaf/coraza-caddy) baked in via
  `xcaddy`, serving the built dashboard SPA and running the actual WAF site
  block. Shares the `caddy-config` volume with `backend` so both containers
  see the same live Caddyfile.
- **`test-app`** (`docker/TestApp.Dockerfile`) — the repository's small,
  deliberately vulnerable demo app, so `docker compose up` gives you
  something to protect immediately and the README's curl checks have a
  target. It listens on `8080` inside the container and is published on the
  host as `127.0.0.1:8082` only — that loopback mapping is the `:8082` origin
  port, and it is deliberately not reachable from anywhere but this machine.
  Swap it for your real application — see below. Never expose it publicly.

## Pointing this at your real application

Edit `docker/Caddyfile`'s second site block — the `:80` one, which is the
public, WAF-inspected entry point:

```caddyfile
:80 {
    reverse_proxy test-app:8080

    # @@CATWAF_WAF_START@@  ...CatWAF's managed WAF block...  # @@CATWAF_WAF_END@@
}
```

Change only the `reverse_proxy` line. Everything between the
`@@CATWAF_WAF_*@@` markers is regenerated by CatWAF on every WAF change.

Two options:

- **Your app also runs in this compose file** — add it as another service,
  then change `test-app:8080` to `your-service-name:port`. If you want that
  origin addressable from the host as well, give it the same loopback
  mapping `test-app` uses (`"127.0.0.1:8082:<its internal port>"`); if you
  don't, drop the mapping entirely and reach it only through `:80`.

  To serve it publicly over HTTPS, replace `:80` with your real domain —
  Caddy provisions the certificate itself, and `443` is already published in
  `docker-compose.yml`.
- **Your app runs elsewhere** (already deployed, a different host) — point
  at wherever it's actually reachable from the `caddy` container, e.g.
  `reverse_proxy host.docker.internal:3001` (Docker Desktop) or a real
  hostname/IP reachable from inside the container network.

After changing it, `docker compose restart caddy` (the file lives on the
shared `caddy-config` volume, so `backend`'s later WAF changes keep applying
to whichever site block CatWAF's own managed configuration block is already
in — same mechanism as the non-Docker setup, see
[reverse-proxy.md](reverse-proxy.md)).

## No Docker socket required

Earlier versions of CatWAF mounted the host's Docker socket
(`/var/run/docker.sock`) into the `backend` container so it could run
`docker exec catwaf-caddy caddy reload ...`. **That is gone.**

Docker socket access is effectively root-equivalent access to the host:
anything that can execute commands inside the backend container could, via
that socket, control every other container and in practice the host itself.
For a security product that was the wrong trade to ask anyone to make.

CatWAF reloads Caddy over **HTTP on a permissioned Unix socket**:

- `caddy` listens on `unix//run/catwaf-admin/admin.sock|0660`.
- Only Caddy and the backend mount the socket volume. The origin container
  cannot connect to the configuration API over the compose network.
- `backend` uses `CADDY_ADMIN_SOCKET=/run/catwaf-admin/admin.sock`.
- `backend/services/caddy.js` prefers a local `caddy reload` when the binary
  is present and falls back to `POST /load` on the admin API. The backend
  image includes the same locked Caddy binary for offline validation. It
  contains no Docker calls at all.

Both containers also run with `no-new-privileges:true`.

Socket ownership and group permissions are the access control. Do not mount
this volume into application containers. Caddy's API has no application login.
Existing named volumes keep their old Caddyfile and permissions across image
rebuilds: follow the [security migration notes](security-audit-2026-10-16.md)
when upgrading an existing stack.

## Hardening

`docker-compose.yml` applies a few conservative container-level measures on top
of `no-new-privileges:true`:

- **`cap_drop: ["ALL"]` on `backend`** — the API runs as the image's
  unprivileged `node` user and listens on high ports (`:8000`) only, so it
  needs no Linux capabilities and now runs with none.
- **`cap_drop: ["ALL"]` + `cap_add: ["NET_BIND_SERVICE"]` on `caddy`** — Caddy
  serves public traffic on `:80`/`:443`, and binding those privileged ports
  requires `NET_BIND_SERVICE`; that single capability is granted back after
  dropping all others. Caddy is deliberately *not* run read-only, since it
  writes certificates and live config to its volumes.
- **Separate service identities** — backend runs as UID 1000; Caddy runs as
  UID 1001 with shared group 1000. Never change Caddy to UID 1000: that would
  let it read the backend's owner-only database through the asset mount.
- **Health checks** — backend checks `/healthz`, Caddy checks its local
  dashboard listener, and the demo checks its HTTP listener. These are liveness
  checks; the separate isolation test verifies actual WAF blocking.
- **Demo containment** — the demo uses a read-only root filesystem, no Linux
  capabilities and a temporary `/tmp` mount.
- **`tmpfs: [/tmp]` on `backend`** — `/tmp` becomes an in-memory mount instead
  of persistent storage in the container's writable layer.
- **JSON log rotation** on `backend` and `caddy` (`max-size: 10m`,
  `max-file: 3`) so container logs cannot grow unbounded on the host.

## Data & config persistence

Named volumes:

- `catwaf-data` → `/app/data` in `backend` — the SQLite database.
  Also mounted read-only into Caddy for generated assets; the database itself is mode 0600.
- `caddy-admin` → `/run/catwaf-admin` in Caddy and backend — the admin socket.
- `caddy-data` → `/data` in Caddy only — certificate private keys, ACME
  accounts and the internal CA. Preserve and back up this volume.
- `caddy-runtime-config` → `/config` in Caddy only — saved runtime
  configuration. The managed Caddyfile remains in `caddy-config`.
- `coraza-logs` → `/var/log/coraza` in Caddy and backend — sensitive audit logs.
- `caddy-config` → `/etc/caddy` in both `backend` and `caddy` — the live
  Caddyfile and Coraza list directory. Seeded from `docker/Caddyfile` the
  first time the volume is created (standard Docker behavior — an empty
  named volume mounted over a directory that has content in the image gets
  populated from that image directory once), and left alone after that, so
  your edits and CatWAF's applied WAF changes persist across
  `docker compose restart` / `down` / `up`.

`docker compose down` preserves these named volumes. `docker compose down -v`
destroys all of them, including the database and TLS identities. Configuration
snapshots do not back up certificate private keys or the entire event database;
use the database backup/restore procedure and separate volume backups.

**Upgrading an existing stack:** before recreating Caddy with the new named
volumes, stop Caddy and copy its existing `/data` and `/config` contents to
private backups (`docker cp` works with a stopped container). Inspect its
mounts with `docker inspect` to locate any old anonymous volumes. Restore the
contents into the new volumes, preserving paths, before starting Caddy; set
their ownership to UID 1001 / GID 1000. Keep the old container/volumes and backups
until HTTPS and certificate fingerprints are verified. Mounting new empty
volumes without migrating the old data replaces the TLS identity and can cause
unnecessary certificate issuance. Never mount these volumes into the origin.

## Building without Compose

```bash
docker build -t catwaf-backend .
docker build -t catwaf-caddy -f docker/Caddy.Dockerfile .
```

Useful if you're integrating these images into an existing orchestration
setup rather than using this repo's compose file directly.

Runtime images use Node 24 on Alpine and omit npm/yarn. Install dependencies and
build the dashboard when building images, rather than running the native setup
wizard inside a container. Database restore uses a stopped-stack, one-shot
backend container; see [security-recovery.md](security-recovery.md).

When upgrading existing volumes from the root-running Caddy image, stop and
back up the stack first. Preserve certificate storage, and set the ownership
of Caddy's `/data` and `/config` contents to UID 1001 / GID 1000. Shared
configuration, audit-log and admin-socket directories need group 1000 and the
documented setgid permissions. Do not change the database ownership or make it
group-readable. Image rebuilds do not repair existing volume ownership.

## Label autoconfiguration

Use the optional [metadata bridge override](../compose.autoconf.yml) and the
[Docker controller guide](orchestration.md#docker) to publish labelled application
routes automatically. The backend receives a restricted metadata socket, never
the engine socket. Kubernetes deployment is documented in the same guide.
